# 验收报告：真实训练闭环

> 生成时间：2026-11-10　版本：v1.1.0+

## 一、这份报告回答什么

平台要回答的核心问题只有一个：**选了数据集、点了开始，能不能真的训练出东西来？**

答案是可以。并且有可对比的证据，而不是"跑通了"三个字。

## 二、决定性证据：一次失败与一次成功的对照

| | `smolvla-pick1028-001` | `smolvla-pick1028-002` |
|---|---|---|
| 训练参数 | batch=8, workers=4, 500 步 | batch=8, workers=4, 500 步 |
| 镜像 | 同一个 | 同一个 |
| Pod 的卷 | datasets, checkpoints | **dshm, datasets, checkpoints** |
| 结果 | **FAILED（29 秒）** | **SUCCEEDED（193 秒）** |
| 失败原因 | 第 0 步 `DataLoader worker killed by signal: Bus error` | 无 |
| loss 点数 | 0 | **500** |

唯一差别是 `/dev/shm` 从容器默认的 64MB 变成 4Gi。这不是猜测——
两个任务的 Pod 定义可以直接 `kubectl get pytorchjob ... -o jsonpath` 对上。

## 五、几个诚实的说明

### 1. 我曾经把测试数据当成真实数据汇报过

早期冒烟镜像写出的 loss 是脚本生成的衰减序列，我一度说成"loss 曲线可用"。
真正的 SmolVLA 训练在那之后很久才产出第一条真实 loss。
假绿比真红危险，这一条记在这里。

### 2. 指标链路修了四轮才生效

模块路径错 → 父进程 hook 不传子进程 → 输出目录被平台预创建导致框架拒绝 →
产物写进子目录。每轮都以为修好了。
根因是**每轮只验证了"以为出错的那一环"**，没有端到端跑完整链路。

### 3. 30 步能跑通不代表系统能跑

30 步用的是 batch=2 / workers=2，在 64MB 共享内存下压力小。
换成 batch=8 / workers=4 立刻暴露问题。
**用小参数验证环境是没有意义的。**

### 4. 当前不适合直接对外的部分

- **鉴权默认关闭**：所有访问者都是 admin，能取消他人任务。多令牌已实现，
  改一个环境变量即可启用，但默认仍是 off（内网单机自用的取舍）
- **无高可用**：单节点、单副本 Web、SQLite。节点挂就是全挂
- **训练规模**：500 步约 3 分钟，验证了链路与收敛趋势，
  但没有跑过真正需要数小时的完整训练

## 六、长时间训练稳定性（3000 步 / 17 分钟）

500 步只跑 3 分钟，不足以说明系统能支撑真实训练。补跑了一次 3000 步。

### 结果

| 项 | 500 步 | 3000 步 |
|---|---|---|
| 任务 | `smolvla-pick1028-002` | `smolvla-pick1028-003` |
| 耗时 | 193 秒 | **1020 秒** |
| 状态 | SUCCEEDED | **SUCCEEDED** |
| 指标点数 | 500 | **3000** |
| 产物 | 2.5 GB | **3.7 GB** |
| loss 末段 | 0.080 | **0.041** |

### 收敛

| 分段 | loss 均值 |
|---|---|
| 第 1/6 段 | 0.250 |
| 第 2/6 段 | 0.083 |
| 第 3/6 段 | 0.060 |
| 第 4/6 段 | 0.049 |
| 第 5/6 段 | 0.041 |
| 第 6/6 段 | 0.041 |

最低 0.0172。从 500 步的 0.08 继续降到 0.04，说明**继续训练确实在改进**，
不是过早饱和。

### 无内存泄漏

| 时刻 | 显存占用 |
|---|---|
| 1638 步 | 4332 MiB |
| 2572 步 | 4334 MiB |
| 结束 | 稳定 |

显存几乎不随步数变化。这是长时间运行最重要的健康信号——
如果每 100 步涨一点，几小时后必然 OOM。

grad_norm 全程 0.26~14.27，均值 0.94，无爆炸、无消失。

## 七、本轮发现的队列级故障

验证过程中撞到一个能让平台「假死」的问题，值得单独记一笔。

### 现象

提交两个任务后，后一个永远 QUEUED。GPU 明明是空的。

### 根因

`smoke-pick1028-001` 用的镜像 `vla-smoke:latest` 已被删除，pod 处于
ImagePullBackOff。但 Kueue **已经把它准入并分配了 GPU 配额**，
它就一直重试、一直占着配额，后面的任务全部拿不到资源。

用户看到的是「排队中」，完全不知道是被一个僵尸任务挡住了。

### 修复

提交时增加镜像可用性检查（`image_unknown` 告警）。

这里有个硬限制必须说明：**Web 进程查不到节点上的镜像列表**——
容器运行时不在 Web pod 里，Kubernetes API 也不暴露本地镜像。
所以只能按「历史上有没有任务用过这个镜像」推断，不完美。

落成 warning 而不是 error，因为刚构建好、还没跑过的镜像也是合法的，
报 error 会挡住正常使用。短名镜像额外提示写成全路径，因为它最容易
去远端拉取然后 403。

### 顺带修掉的

- 排队位置恒为 null：Kueue 的 Workload 名是 `pytorchjob-<任务名>-<后缀>`，
  而查表用的是任务名，键值对不上，永远查不到。用户排队时看不到排第几。
- Bus error 被归成 `python_error`，建议是「查看 traceback」——
  真实原因是共享内存不足，用户盯着 torch 内部栈想不到去改 /dev/shm。

## 八、下一步该做什么

前两版报告里列的三条建议，已经完成两条：

- ~~启用 token 鉴权~~ —— 已完成，admin/user 两角色，403 隔离实测有效
- ~~跑数小时的完整训练~~ —— 做到 3000 步 / 17 分钟，显存全程无增长。
  但**没有验证断点续训**（`--resume` 路径），也没跑过真正数小时的样本
- 高可用 —— 仍未做，需要多节点

剩下的按性价比排序：

1. **断点续训**：训练中断后能否从 checkpoint 继续。当前只有 `resume=false`
   的路径被验证过。真实训练被抢占或节点重启时，这一条决定了几小时算力是否白费。
2. **高可用**：单节点、单副本 Web、SQLite。节点挂就是全挂。
   这是当前架构最大的单点，也是「企业级」这个说法最站不住的地方。
3. **更长时间的训练**：3000 步不会暴露所有问题。磁盘占用、
   checkpoint 数量、指标文件大小都会随训练时长线性增长，
   需要一次真正小时级的验证才能确认这些维度不会失控。

### 一个诚实的总结

这个平台现在能可靠地跑真实的 VLA 微调，有完整的可观测、诊断、权限与治理。
但它仍然是一个**单机系统**。说它是「企业级」需要同时满足三个条件：
不因单点故障整体不可用、有人能随时接手运维、以及经过长时间真实负载验证。
第一条目前不满足，后两条取决于使用方式。


## 附：如何自己复核

```bash
# 看两个任务的 Pod 定义差异
kubectl -n vla-training get pytorchjob smolvla-pick1028-001 \
  -o jsonpath='{.spec.pytorchReplicaSpecs.Master.template.spec.volumes[*].name}'
# 输出: datasets checkpoints

kubectl -n vla-training get pytorchjob smolvla-pick1028-002 \
  -o jsonpath='{.spec.pytorchReplicaSpecs.Master.template.spec.volumes[*].name}'
# 输出: dshm datasets checkpoints

# 看 500 步的 loss
curl -s "http://172.16.122.37:30080/api/v1/jobs/smolvla-pick1028-002/metrics?limit=500" \
  | python3 -c "import sys,json;d=json.load(sys.stdin);l=[i['loss'] for i in d['items']];print(len(l),'点',sum(l[:20])/20,'->',sum(l[-20:])/20)"
```
