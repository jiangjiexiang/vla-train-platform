# VLA 训练平台 v1.0 · 使用手册

面向算法工程师。读完你能独立完成：选数据集 → 选配方 → 提交 → 看排队 → 看曲线 → 失败自查。
不需要懂集群运维；第 9 节术语表对少量基础设施词汇做了解释。

- 平台入口：`http://<服务器IP>:30080`（下文用 `$S` 代指，例如 `S=http://172.16.122.37:30080`）
- 本文所有命令都可以直接复制，只需把 `$S` 换成实际地址
- 每条说明都来自平台当前实现；界面文案与真实接口响应（`/api/v1/...`）一致

### 1.2 三步发起训练

| 步骤 | 操作 | 注意 |
|---|---|---|
| 1 | 在「第一步 · 选择数据集」点数据集卡片 | 只有「可用」和「有警告」的卡片能点；「不可用」卡片置灰，鼠标悬停可看全部错误原因 |
| 2 | 在「第二步 · 选择训练配方」选配方 | 平台只列出**格式兼容**的配方；换数据集后配方会自动回落到第一个兼容项 |
| 3 | 填任务名（可留空）→ 点「加入训练队列」 | 留空时平台生成 `<配方短名>-<数据集>-<三位序号>`，例如 `smolvla-pick1028-001` |

点击后平台会先做**预检**（第 5 节）：通过则创建任务并自动跳转到任务详情页，页首提示「任务 xxx 已加入训练队列」；
有警告（如数据集有警告、样本偏少）会弹窗「预检发现一些提醒，仍要加入队列吗？」，点「仍然提交」继续；
有错误则顶部红条拦住，按建议处理。

任务名规则：只允许**小写字母、数字和中划线**，不能以中划线开头或结尾，最长 50 字符；重名会返回 409「任务名已被占用」，换一个名字或清空让平台生成。

### 2.1 快速开始（首页）
- 「第一步 · 选择数据集」右上角有搜索框和「重新扫描」按钮。重新扫描会触发一次扫描，把目录变化同步进来。
- 卡片上显示：状态（可用/有警告/不可用）、格式、集数、帧数、时长、相机路数、state/action 维度、体积。
- 「第二步 · 选择训练配方」右上角会写「已选 xxx（格式），N 个配方兼容」。
- 「第三步」里就是表单：任务名、优先级（低/普通/高）、可折叠的「高级参数」。
- 右上角「需要更多控制？使用高级提交」是通往 `/advanced/submit` 的入口。

### 2.2 数据集
- 顶部四个统计卡：数据集总数 / 可用 / 有警告 / 不可用，下方附累计帧数。
- 表格列为：名称、状态、格式、集数、帧数、时长、相机、维度（state/action）、体积、扫描时间、操作。
- 点一行打开右侧抽屉：基本元数据（路径、任务描述、相机名、动作名、深扫描/浅扫描与扫描时间…）+ **问题清单**（每条带级别与 issue 代码）。
- 抽屉右上「用此数据集开始训练」会跳到首页并预选该数据集；不可用（`unusable` / `error`）的数据集该按钮置灰。
- 「重新扫描」按钮 = 请求 `?refresh=true`，平台会重新扫描目录修改时间有变化的数据集。

### 2.3 训练配方
- 折叠列表，每个配方标题行显示：显存估算、GPU 卡数、支持的数据集格式标签、描述。
- 展开后是「参数清单」表：参数名、参数标签、类型、默认值、可选值/范围、说明。
- **页面只读**，修改配方需要管理员改配置文件并重新发布，页面上改不了。

### 2.4 任务列表
- 状态筛选：全部/排队中/运行中/已成功/已失败/已取消；可按任务名搜索。列表每 4 秒刷新。
- 关键列：
  - **排队位置**：排队中显示「第 N 位」和预计等待，其他状态显示「—」。
  - **Kueue / Pod**：第一位是队列放行状态（Pending / Admitted / Finished），第二位是容器状态（Pending / Running / Succeeded / Failed）。列名是集群术语（见术语表），看「状态」列即可。
  - **运行时长**：从开始执行算起（排队时间不计入）。
- 顶部会出现配额横幅，例如「GPU 配额：已用 1 / 2 卡 · 活跃任务：1 / 3（按当前页的排队中/运行中任务统计）」。
- 操作列：取消（排队中/运行中）、克隆（复制一份提交参数，新任务名加 `-copy`）。
- 注意：克隆产生的是一个**普通任务**，不带配方/数据集标签，因此不会计入「同配方历史耗时」，也不影响 ETA 估算口径。

### 2.5 任务详情（重点）

| 区块 | 内容 | 什么时候看 |
|---|---|---|
| 失败诊断卡 | 红色卡片：一句话摘要 + 「建议：…」+ 折叠的「查看原始证据」 | 任务失败时出现在页面最上方 |
| 排队位置条 | 「排队中：排在第 N 位（前面还有 N-1 个任务），预计等待约 X 分钟」 | 排队中 |
| 事件 / 消息 | 平台对整个任务的一句话说明，如「等待资源放行」「已放行但容器未就绪」 | 任何时候，用来确认卡在哪个环节 |
| 提交参数 | 任务名、提交者、镜像、GPU 数、优先级、训练命令、环境变量、标签、**Checkpoint 目录** | 想确认「参数到底生效没有」 |
| 放行状态、容器状态、提交/开始/结束时间 | 卡片标题是集群术语（Kueue / PyTorchJob、Pod），内容就是时间线信息 | 排查时间线 |
| 训练 Loss 曲线 | 每个点来自 /checkpoints/<任务名>/metrics.jsonl，每 10 秒刷新 | 训练中/已结束 |
| 事件 | 系统事件的类型、原因、次数、最近发生时间 | 镜像拉取失败、调度失败等 |
| 训练日志 | 末尾 500 行，自动跟随；向上滚动会暂停跟随 | 定位 traceback |

说明：当前发布版本的「任务详情」页**没有独立的阶段时间轴组件**——时间信息分散在时间卡片和「事件/消息」里。
平台接口 `/api/v1/jobs/<任务名>/timeline` 已经提供阶段时间轴数据，含义见 6.5。

### 2.6 队列
- 每个队列一张卡片：`LocalQueue: default`、`ClusterQueue: vla-cluster-queue`。
- 统计：**GPU 配额 / 已使用**（进度条，用满变红）、**等待放行**（排队任务数）、**已放行**（运行中任务数）。
- 下方表格列出该队列里的工作负载及其状态、优先级、创建时间。
- 注意表格会包含**已结束的历史工作负载**，所以条目数会大于当前任务数，以任务列表为准。

### 2.7 高级提交（什么时候需要它）
快速开始已经覆盖 95% 的场景。出现下列情况才用高级提交（`/advanced/submit`，旧地址 `/submit` 会自动跳转到它）：

| 场景 | 为什么快速开始做不到 |
|---|---|
| 用配方之外的镜像做一次性验证 | 配方固定了镜像，高级提交可以自选镜像 |
| 需要自己写整条命令（改了训练脚本参数名、跑评估脚本） | 快速开始只能通过配方声明的参数生成命令 |
| 需要额外环境变量 | 快速开始不暴露环境变量输入（配方内部才带 `DATASET_ROOT` 等） |
| 需要多节点/指定 GPU 拓扑 | 一键训练固定单节点、`gpu_count` 卡 |
| 复现同事的任务 | 在任务列表点「克隆」比手抄参数更稳 |

高级提交建出的任务**不会**自动带上配方/数据集标签，也**不经过**第 5 节的配方类预检。别用它绕开预检。

## 3. 理解数据集

### 3.1 平台怎么判断「可用 / 有警告 / 不可用」

平台扫描 `PLATFORM_DATASETS_HOST_PATH`（容器内 `/datasets`）下每个子目录，每个子目录是一个 LeRobot 数据集（目录名即数据集 ID）。
扫描分两档：浅扫描只读 `meta/info.json` 和目录结构；深扫描额外读 parquet 列、视频目录、`meta/stats.json`。
**列表页与一键训练用浅扫描结果**，快但看不到数据文件层面的问题。

规则很简单（按最严重的级别取）：

| 状态 | 徽标 | 判定 | 能否一键训练 |
|---|---|---|---|
| `ready` | 可用（绿） | 没有任何 error 或 warning | 能 |
| `warning` | 有警告（黄） | 有 warning，没有 error | 能（提交时弹窗确认） |
| `unusable` | 不可用（红） | 存在任意 error 级 issue | 不能，卡片置灰；接口直接 422 |
| `error` | 扫描失败（红） | 扫描该目录时抛异常 | 不能 |
| `scanning` | 扫描中 | 正在扫描 | 短暂出现，稍后刷新 |

`info` 级 issue **不影响**状态，只在问题清单里提示。

### 3.2 常见 issue 代码表

代码来自扫描器的 issue 定义。级别为 `error` 的一定要让管理员在宿主机上修数据；warning 通常可以先训练。

| code | 级别 | 含义 | 怎么修 |
|---|---|---|---|
| `missing_info` | error | 缺 `meta/info.json`，不是有效 LeRobot 目录 | 确认目录没有指错；重新导出/下载完整数据集 |
| `invalid_info` | error | `meta/info.json` 不是合法 JSON | 文件可能被中断写入，重新生成或从备份恢复 |
| `missing_feature` | error | `info.json` 的 features 里缺 `observation.state` 或 `action` | 检查导出流程，确认动作列被写入 |
| `no_episode` | error | `total_episodes` 为 0 | 采集/转换没完成，重新导出 |
| `no_frame` | error | `total_frames` 为 0 | 同上 |
| `missing_data_dir` | error | 缺 `data/` 目录 | 文件没拷全，重新同步 |
| `scan_failed` | error | 扫描过程抛异常（权限等） | 找管理员看平台日志与目录权限 |
| `no_data_file` | error（深扫描） | `data/` 下没有 `chunk-*/*.parquet` | 采集未完成，重新导出 |
| `missing_column` | error（深扫描） | parquet 缺 `observation.state` / `action` 列 | 数据损坏或格式不对，重新导出 |
| `missing_videos_dir` | error（深扫描） | `info.json` 声明了视频，但没有 `videos/` | 视频没拷过来，补拷 |
| `missing_camera_video` | error（深扫描） | 某个相机在 `videos/` 下没有目录 | 补拷该相机录像，或从 `info.json` 去掉该相机 |
| `no_camera` | warning | 没有任何图像/视频特征 | 采集时没开相机；视觉策略无法训练，重录 |
| `tiny_dataset` | warning | 少于 1000 帧 | 补数据，或预期效果差 |
| `data_unreadable` | warning（深扫描） | parquet 元数据解析失败，文件可能损坏 | 从备份重拷该文件 |
| `empty_camera_video` | warning（深扫描） | 相机目录里没有 mp4 | 补录 |
| `zero_video` | warning（深扫描） | 视频文件大小为 0 | 补录 |
| `invalid_stats` | warning（深扫描） | `meta/stats.json` 不是合法 JSON | 删除它让平台重算，或重新生成 |
| `dim_mismatch` | info | state 维度与 action 维度不同 | SmolVLA 等要求两者一致，训练前确认 |
| `missing_stats` | info（深扫描） | 缺 `meta/stats.json` | 平台训练时会自动计算归一化统计 |
| `incomplete_stats` | info（深扫描） | stats 缺 action 归一化统计 | 平台训练时会补齐 |
| `missing_quantiles` | info（深扫描） | 缺 q01/q99 分位数 | 训练 π0/π0.5 前需要补（见 3.4） |
| `leftover_backup` | info | 目录里有 `meta.bak/`、`data.bak/`、`videos.bak/` | 移出数据集目录，避免工具按 glob 重复计数 |

### 3.3 「动作维度几乎不动」是什么意思

平台深扫描会从 `meta/stats.json` 计算每一维的 min / max / mean / std / range，并标记 `static`：
**极差小于 1e-4，或 标准差不足极差的 1%**，就认为这一维「几乎不动」。

一维几乎不动，通常意味着：
- 采集时这个关节没被用到（遥控只动了手臂没动底盘/夹爪）；
- 或该维的标定/单位有问题（值域被压扁）。

为什么必须关注：训练 loss 会照样下降，但策略在这个维度上永远输出同一个值——**数据分布没覆盖到的动作，模型学不会**。
上线后发现「某个关节死活不动」，通常要回到这里查。看到 `static_dims` 非空，就对照 `action_names` 看是哪几个关节，回去补采集。

### 3.4 分位数统计 q01/q99 对哪些模型有影响

`meta/stats.json` 里 action 的 `q01`/`q99` 是 1%/99% 分位数，用于按分位数做动作归一化。

| 模型 | 是否需要 q01/q99 | 缺了会怎样 |
|---|---|---|
| π0 / π0.5（openpi 配方） | **需要**（QUANTILES 归一化） | 训练启动即抛 `ValueError`，任务失败 |
| SmolVLA | 不需要 | 不受影响 |
| 环境冒烟测试 | 不需要 | 不受影响 |

平台在深扫描时会记一条 `missing_quantiles`（info 级）；预检时把它提升成**提交前的明确提示**，并说明只影响 π0/π0.5。
补法：先在数据旁跑 lerobot 的 `augment_dataset_quantile_stats.py`，重新扫描后再提交。注意 openpi 配方本身只支持 LeRobot v2.0/v2.1，v3.0 数据还需先转换格式。

## 4. 理解训练配方

### 4.1 配方是什么

一个配方 = **镜像 + 入口命令 + 支持的数据集格式 + 参数模板 + 默认值 + 显存/卡数预估 + 可选环境变量**。
平台用它把你选的参数拼成最终命令行，例如冒烟测试生成的就是 `python /app/train.py --steps 15`。

参数分三层，对应「谁能改」：

| 层 | 内容 | 谁能改 |
|---|---|---|
| L1 配方 | 镜像、入口、数据集格式、默认值 | 管理员（你只能选） |
| L2 常用参数 | 配方声明的参数，如 `steps`、`batch_size` | 你，展开「高级参数」后改 |
| L3 高级参数 | 同上，更少用到的项 | 你 |

参数取值优先级：**你的输入 > 配方默认值 > 参数模板里的 default**。你不填的项用默认值，界面会在输入框下方显示「默认 X」。

### 4.2 三个内置配方

| 配方 | 适用场景 | 支持格式 | 卡数 | 显存预估 |
|---|---|---|---|---|
| 环境冒烟测试 `smoke-test` | 新环境上线前验证显卡、数据挂载、checkpoint 写入；几秒完成 | v3.0 / v2.1 / v2.0 | 1 | 2 GB |
| SmolVLA 微调 `smolvla-finetune` | 单卡 4090 的抓取类任务，当前主力方案 | v3.0 / v2.1 / v2.0 | 1 | 12 GB |
| π0.5 LoRA 微调 `openpi-pi05-lora` | 需要 openpi π0.5 能力，4090 只能跑 LoRA | **仅 v2.1 / v2.0** | 1 | 24 GB |

**环境冒烟测试**：唯一需要理解的是不要乱改，保持 5 步即可。它的作用是把「环境问题」和「训练问题」分开。

**SmolVLA 微调** 关键参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| 训练步数 `steps` | 2000 | 总优化步数；4090 上约 1.5 步/秒，2000 步约 20 多分钟 |
| batch size `batch_size` | 16 | 4090 实测 bs=16 约 5.6 GiB，bs=64 约 19.5 GiB |
| 梯度累积 `grad_accum` | 1 | 显存不够时用它放大有效 batch（不改显存峰值） |
| 保存间隔 `save_freq` | 500 | 存到 `/checkpoints/<任务名>/`，任务结束不删除 |
| 日志间隔 `log_freq` | 10 | 打印日志的频率 |
| 数据加载进程 `num_workers` | 8 | 4090 上瓶颈常在 dataloader，建议 8–16 |
| 学习率 `lr` | 1e-4 | 传给 `--policy.optimizer_lr` |
| 设备 `device` | cuda | 一般不改 |
| 续训 `resume` | 关 | 开启后读取输出目录里的 `checkpoints/last` |

**π0.5 LoRA 微调** 关键参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| 训练配置 `config_name` | `pi05_droid` | **必填**，可选 `pi05_droid` / `pi05_aloha` / `pi05_libero` / `pi05_aloha_pen_uncap`；决定模型结构与数据变换，**选错会维度不匹配** |
| 实验名 `exp_name` | 空 | **必填**，输出到 `/checkpoints/<任务名>/<实验名>/` |
| 训练步数 `num_train_steps` | 30000 | 步数大，先用小步数验证通再放大 |
| batch size `batch_size` | 8 | 4090 只能跑 LoRA（全量需 >70 GB 显存） |
| 峰值学习率 `peak_lr` | 5e-5 | |
| 保存间隔 `save_interval` | 5000 | |
| 覆盖已有输出 `overwrite` | 关 | **有破坏性**，会删除同名输出目录 |
| 断点续训 `resume` | 关 | |
| 上报 W&B `wandb_enabled` | 关 | 需要集群已配置 W&B |

必填参数（`config_name`、`exp_name`）不填，表单会直接拒绝提交。

### 4.3 高级参数面板怎么用

- 面板默认折叠，标题形如「高级参数（可选，共 9 项，默认使用配方推荐值）」。
- **留空 = 用默认值**。每个输入框下面的「默认 X」就是留空时会用的值。
- 控件类型：整数/小数是数字框（带最小/最大值），开关是「开启/关闭」，枚举是下拉，其余是文本框。
- **只有你真正改动过的值才会被提交**。你把某个值改回默认值，等同于留空。
- 提交后想确认最终生效值：任务详情的「训练命令」是平台实际执行的完整命令，参数有没有生效一眼可见。

## 5. 提交前会发生什么（预检）

点「加入训练队列」时，平台先调用预检接口（不创建任何任务），再决定后续动作。预检是**同步、秒级**的。

| level | 行为 | 你要做什么 |
|---|---|---|
| `error` | 拦住，不提交；页面顶部红条列出所有 error 及其 `suggestion` | 按建议处理后重新点提交 |
| `warning` | 弹窗「预检发现一些提醒，仍要加入队列吗？」 | 确认无误点「仍然提交」，否则点「返回修改」 |
| `info` | 只提示，不拦截；无 warning 时也会弹窗（因为弹窗条件是「存在 error 以外的任何提示」） | 看一眼即可 |
| 无任何 check | 直接提交 | 无 |

注意两点：
1. **弹窗只看「有没有非 error 的提示」，不看是 warning 还是 info**。info 级的「显存预估」「任务会先排队」也会让你确认一次，这是正常的。
2. 预检接口本身不可用时，前端会退化为直接提交，后端在创建任务时**再预检一次**并拦截 error。所以拦不住的情况不会发生，只是错误提示出现得晚一些。

### 5.1 预检检查项

| code | level | 触发条件 | 怎么解决 |
|---|---|---|---|
| `dataset_unusable` | error | 数据集状态为 `unusable` / `error` | 按数据集页问题清单修数据后重新扫描；常见是缺 `meta/info.json`、没有 data 文件、视频缺失 |
| `no_camera` | error | 数据集没有任何相机 | 采集时未开相机，需重新采集；不要指望换配方解决 |
| `format_mismatch` | error | 数据集格式不在配方支持列表里 | 换兼容配方（页面会自动只列兼容的），或先转换数据格式（v3.0 → v2.x） |
| `gpu_exceeds_total` | error | 申请卡数超过集群 GPU 总数 | 减卡；一键训练的配方都是 1 卡，基本不会触发 |
| `dataset_warning` | warning | 数据集状态为 `warning` | 通常可继续；效果不佳时先回头查这些警告 |
| `few_episodes` | warning | episode 少于 10 个 | 样本偏少，易过拟合；建议至少几十个 episode，或降低步数 |
| `few_frames` | warning | 帧数少于 1000 | 数据太少，先补采集再训练 |
| `missing_quantiles` | info | 数据集缺 q01/q99 | 只影响 π0/π0.5；用对应的 augment 脚本补分位数 |
| `vram_estimate` | info | 配方声明了显存预估且集群 GPU 总数已知 | 报 CUDA OOM 时先减 batch size |
| `will_queue` | info | 当前空闲卡数 < 本次申请卡数 | 正常现象，前面任务结束会自动开始 |
| `gpu_total_unknown` | info | 读不到集群 GPU 总数 | 任务一直排队时再排查 |

真实返回示例（`smoke-test` + `pick1028`）：

```bash
$S=http://172.16.122.37:30080
curl -s -X POST $S/api/v1/runs/preflight -H 'content-type: application/json' \
  -d '{"recipe_id":"smoke-test","dataset_id":"pick1028"}'
# {"ok":true,"checks":[{"level":"info","code":"vram_estimate","message":"该配方预计占用约 2.0 GB 显存",...}],
#  "summary":{"errors":0,"warnings":0}}
```

把 `recipe_id` 换成 `openpi-pi05-lora`、数据集仍是 `pick1028`（v3.0），会得到 `ok:false` + `format_mismatch`。

## 6. 任务运行中

### 6.1 排队位置怎么看

`queue_position` 的语义是**「我自己排第几位」，队首为 1**。所以「前面还有几个人」= `queue_position - 1`。
任务详情页会同时给出两种说法：「排在第 3 位（前面还有 2 个任务）」，避免误读。
只有排队中的任务有位置；开始运行或结束后该字段为空。

位置只统计**同一队列内尚未放行的任务**，按进入队列的时间先后排序。

### 6.2 排队根因的 5 种情况

平台会对排队中的任务分析根因，给出可直接执行的动作。对照下表判断你遇到的是哪一种：

| code | 平台标题 | 典型表现 | 你该做什么 |
|---|---|---|---|
| `quota_full` | 队列配额已满 | 队列 GPU 全部分给了正在运行的任务 | **什么都不用做**，任何一个任务结束你会自动开始。确认那些任务确实可以中断时，才去取消它们 |
| `high_priority` | 被更高优先级任务插队 | 有高优先级任务排在你前面 | 等比你先开始更久，或等待；确需抢时间可在提交时选「高」优先级 |
| `user_quota` | 个人配额不足 / 个人任务数已达上限 | 你已用的卡数 + 本次卡数 > 个人上限，或活跃任务数达上限 | 取消自己的旧任务（取消后立即释放配额）；确实不够时申请提额 |
| `fragmentation` | 资源碎片 | 队列还有空闲卡，但不够本次申请 | 等前面任务整体释放；或降低本次卡数 |
| `resource_group` | 集群队列配置异常 | 读不到队列 GPU 配额 | 你自己的任务没救，找管理员 |

判定顺序就是上表从上到下（`fragmentation` 的条件是「有空闲但不够本次申请」，`quota_full` 是「一点空闲都没有」，两者互斥）。
**平台不会瞎猜**：如果没有足够信息判断根因，不会给出错误的建议。

### 6.3 ETA 是估算值，不是承诺

- 估算方法：按位置累加前面任务的「预计剩余时间」。
- 典型耗时优先取**同配方历史任务时长的中位数**（成功和失败的都算，取消的不算）。
- **没有历史数据**时，假设一个任务平均跑 30 分钟，并在界面显示「约 X 分钟」+ 一句说明「当前集群没有该配方的历史数据，等待时间按默认假设估算，仅供参考」。
- 高优先级插队、任务实际时长偏离历史、集群故障都会让 ETA 失准。**用它判断「要不要现在等」，不要用它当排期承诺。**

### 6.4 loss 曲线从哪来

- 训练脚本每步把指标追加写入 `/checkpoints/<任务名>/metrics.jsonl`，每行一个 JSON，例如：
  `{"step": 100, "loss": 0.0234, "lr": 1e-4, "epoch": 0.12}`
- 平台从宿主机读同一份文件来画图，**任务结束后曲线仍在**，可以随时回看。
- 有数据的条件：这个文件存在。刚开始的任务、旧任务、没打过日志的脚本都会是「暂无数据（训练脚本还没有写出 metrics.jsonl）」。
- 曲线区域右上角会显示「N 个点」或「N 个点（仅显示最近部分）」；同一个 step 重复写以最后一次为准。
- 页面每 10 秒刷新一次，曲线卡片里的大幅抖动是真实数据，平台不做平滑。

### 6.5 阶段时间轴各节点含义

| 阶段 key | 显示名 | 含义 | 卡在这里通常因为 |
|---|---|---|---|
| `submitted` | 已提交 | 任务对象已创建 | — |
| `queued` | 已入队 | 进入队列等待资源 | — |
| `admitted` | 已准入 | 队列已分配资源给你 | — |
| `image` | 拉取镜像 | 容器开始启动（镜像加载） | 镜像不存在/未导入，看事件里的错误 |
| `container` | 容器启动 | 训练进程已开始在容器里执行 | 启动脚本报错，看日志 |
| `running` | 训练中 | 训练循环在跑 | — |
| `finished` | 已结束 | 成功或失败 | 失败时看诊断卡 |

状态取值：`done` 已完成、`current` 进行中（**卡在这里**）、`pending` 未到达、`failed` 失败。时间戳取不到时为空，平台不会编造。

```bash
curl -s $S/api/v1/jobs/<任务名>/timeline
# {"status":"SUCCEEDED","current_stage":"image","items":[{"stage":"submitted","label":"已提交","state":"done","at":"..."}, ...]}
```

### 6.6 checkpoint 在哪、会不会丢

- 每个任务详情「提交参数」最后一行是 **Checkpoint 目录**，形如 `/checkpoints/<任务名>`，这是容器内路径；宿主机上对应 `PLATFORM_CHECKPOINTS_HOST_PATH` 下的 `<任务名>/`。
- 保存间隔由配方的 `save_freq`（SmolVLA，默认 500 步）/ `save_interval`（π0.5，默认 5000 步）控制。间隔越小，磁盘占用越多。
- **Web 端对 checkpoint 目录是只读挂载**：平台能读 `metrics.jsonl` 给你画图，但**不能**替你改文件。
- **在 Web 上「取消」或删除任务，不会删除 checkpoint**。已保存的权重会一直留在宿主机上，需要清理时找管理员。反过来，也别指望在 Web 上删任务来腾空间。

## 7. 任务失败怎么办

### 7.1 诊断卡怎么看

任务失败后，详情页最上方出现红色卡片，三段信息：

| 部分 | 内容 | 怎么用 |
|---|---|---|
| 标题（`summary`） | 一句话说清发生了什么，如「GPU 显存不足」 | 先对号入座 |
| `建议：…`（`suggestion`） | 具体下一步动作 | 照着做 |
| 「查看原始证据」（`evidence`） | 命中的那段日志/事件原文（最多 200 字符） | 拿去和完整日志对照，确认是不是同一个问题 |

诊断按「事件 → 状态消息 → 日志末尾」的顺序找信号；都没命中时归为「训练脚本抛异常」。

### 7.2 诊断码对照表

| code | summary | 下一步 |
|---|---|---|
| `image_pull` | 镜像拉取失败 | 镜像需先导入到节点，且镜像名要写全（如 `vla-smoke:latest`）；找管理员确认 |
| `image_pull_backoff` | 镜像持续拉取失败 | 镜像名拼写错误或没导入节点；确认镜像存在后再重提 |
| `oom_gpu` | GPU 显存不足 | 减 batch size、开梯度累积；也可降输入分辨率、冻结视觉编码器、改用 LoRA |
| `oom_container` | 容器内存超限被杀 | 减 batch / num_workers，或申请提高内存限额 |
| `dataset_missing` | 数据集路径不存在 | 容器内 `/datasets/<id>` 不存在；确认宿主机数据目录有这份数据后重新扫描 |
| `dataset_empty` | 数据集目录为空或不可读 | 检查目录权限与内容 |
| `checkpoint_write` | checkpoint 写入失败 | `/checkpoints` 不可写；找管理员修目录权限 |
| `python_error` | 训练脚本抛异常 | 看日志末尾 traceback；常见是不兼容的参数名、缺依赖、权重路径不对 |
| `module_not_found` | 缺少 Python 依赖 | 镜像里没装该模块；核对镜像版本与被训练代码是否匹配 |
| `permission_denied` | 权限不足 | 容器用户无权访问该路径/文件；找管理员调整目录属主 |
| `evicted` | 运行实例被驱逐 | 节点磁盘或内存不足；清理磁盘或减小任务规模后重试 |
| `config_error` | 参数配置错误 | 数据集与配方/模型参数不匹配；检查格式版本、动作维度、相机数量 |
| `nccl` | 分布式通信失败 | 多卡/多机通信初始化失败；检查各节点版本一致、GPU 可访问 |

（`dataset_empty` 已定义但当前没有匹配规则，实际不会单独命中，现场表现为 `dataset_missing`。）

### 7.3 什么时候需要找管理员

| 现象 | 为什么你解决不了 |
|---|---|
| `resource_group` 排队根因 | 集群队列配置异常 |
| `image_pull` / `image_pull_backoff` | 镜像需要导入节点，普通用户无权限 |
| `checkpoint_write` / `permission_denied` | 宿主机目录权限 |
| `evicted` 反复出现 | 节点磁盘/内存不足 |
| 数据集 `scan_failed`，或 error 级 issue 来自宿主机文件 | 需要改宿主机上的数据文件 |
| 配额不够（`user_quota`）且已无可取消任务 | 配额由管理员在「用户与配额」里调整 |
| 想要新模型/新参数 | 配方由管理员维护，页面只读 |

找管理员时把这三样一起给出：任务名、诊断卡上的 `summary` + `evidence`、以及该任务的事件与日志末尾。对方能秒定位。

## 8. 常见问题 FAQ

**Q1：数据集列表是空的 / 只有少量几个。**
① 点「重新扫描」；② 确认数据放在宿主机数据目录的**直接子目录**下，且每个子目录里有 `meta/info.json`；③ 以 `.` 开头或以 `.tmp`、`.partial` 结尾的目录会被跳过；④ 目录名就是数据集 ID，改名后需要重新扫描。

**Q2：任务一直排队，不动。**
先看任务详情「排队位置」条和根因（6.2）：`quota_full` 只能等；`high_priority` 是被高优先任务插队；`user_quota` 是你自己的配额满了，取消旧任务即可；`fragmentation` 是碎片，等或减卡。都没有提示时，看「队列」页 GPU 是否确实被占满。

**Q3：看不到 loss 曲线。**
曲线只读 `/checkpoints/<任务名>/metrics.jsonl`。① 任务还在排队/刚启动，脚本还没写第一条；② 训练脚本没有按约定写这个文件；③ 训练已进入「训练中」但仍无数据，多半是训练脚本没按约定写该文件——核对脚本里是否写了 `/checkpoints/<任务名>/metrics.jsonl`；镜像自带的训练脚本会写。

**Q4：任务失败，但日志看不懂。**
先看红色诊断卡（7.1），`summary` 已经把你从「一坨日志」拉到具体类别；点「查看原始证据」看命中的那行；再在完整日志里搜 `Error` / `Traceback` / `CUDA`。语义上是 Python 异常而诊断卡给的是 `python_error` 时，就直接读 traceback 的最后几行。

**Q5：参数填了，但好像没生效。**
① 打开任务详情 →「提交参数」→「训练命令」，这是实际执行的完整命令，参数在不在、值对不对一眼可见；② 只有**改动过**的参数才会提交，改回默认值等于没改；③ 参数名必须属于该配方声明的参数，不属于的会被拒绝（未知参数）；④ 若开了「克隆」，克隆出的是原任务的参数快照。

**Q6：配方列表里没有我想要的模型。**
配方由管理员维护、随服务发布，页面只读。当前只有冒烟测试、SmolVLA、π0.5 LoRA 三个。新模型需要管理员新增配方；如果只是想快速验证，可以走「高级提交」用现成镜像跑。

**Q7：选不了想要的数据集（卡片置灰）。**
它被判为「不可用」（存在 error 级 issue）。把鼠标移到卡片上能看到全部错误原因，或在「数据集」页点开该行看问题清单；修好后重新扫描。另外注意：**数据集格式不兼容时卡片不会置灰**，而是在第二步里看不到该配方——例如 π0.5 配方不出现在 v3.0 数据集下。

**Q8：提交时弹窗说「预检发现一些提醒」。**
弹窗只要存在 error 以外的任何提示就会出现，包括 info 级的「预计占用 X GB 显存」「当前空闲卡不够，任务会先排队」。看完确认无误点「仍然提交」；如果是「数据集有 N 条警告」，建议记住这些警告，效果不好时先查它们。

**Q9：取消任务后 checkpoint 还在吗？**
在。checkpoint 目录对 Web 是只读挂载，Web 上的取消/删除只影响任务本身，不会动 `/checkpoints/<任务名>/` 下的文件。

**Q10：为什么「高级提交」建的任务没有排队位置/ETA？**
ETA 依赖「同配方历史耗时」。一键训练会给任务打 `recipe`、`dataset` 标签，高级提交的任务没有这些标签，只能按默认假设估算或显示为空，排队位置仍照常计算。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 队列 | 集群 GPU 的排队通道。资源不够时任务在这里等待，前面任务结束后自动放行 |
| 放行 / 准入 | 队列把资源分配给你、任务从「排队」转为可启动 |
| 配方（Recipe） | 一组预定义的训练方案：镜像、入口命令、支持的数据集格式、参数模板与默认值。你只能选和调参，不能改 |
| 数据集 | 宿主机数据目录下的一个子目录，LeRobot 格式，目录名即数据集 ID |
| 浅扫描 / 深扫描 | 浅扫描只读 `meta/info.json` 与目录结构（快）；深扫描还检查 parquet 列、视频目录与 stats 分布（详情页用） |
| issue | 扫描发现的一条数据集问题，有级别（error/warning/info）与稳定的代码 |
| 预检（Preflight） | 提交前的秒级检查，error 拦住、warning 提示确认、info 只提示 |
| 准入（数据集） | 数据集是否达到「可被一键训练选中」的状态：`ready` 和 `warning` 可用，`unusable` 不可用 |
| checkpoint | 训练过程中保存的模型权重，位于 `/checkpoints/<任务名>/`，Web 端只读，任务结束不删除 |
| `metrics.jsonl` | 训练脚本每步追加一行的指标文件，loss 曲线的数据源 |
| 分位数统计 | `meta/stats.json` 里的 q01/q99，用于按分位数做动作归一化；π0/π0.5 必需 |
| 静态维（static dim） | 标准差远小于极差、几乎不变的动作/状态维度，通常说明采集时没用到该关节 |
| 排队位置 | 任务在队列中的名次，队首为 1；`第 N 位` 表示前面还有 N-1 个任务 |
| ETA | 预计等待时间，按历史耗时估算，仅供参考 |
| 诊断码 | 平台把失败原因归一化后的稳定代码（如 `oom_gpu`），用于快速定位 |
| 优先级 | 低 / 普通 / 高。高优先级任务会排在低优先级任务前面 |
| 容器 / Pod | 任务在集群里的实际运行实例（界面某些区块标题会用到这个词，理解成「跑训练的那台机器上的进程」即可） |
| 镜像 | 打包了训练代码与依赖的运行时，配方里已固定（如 `vla-smolvla:latest`） |
| Kueue / PyTorchJob | 集群里的队列调度与任务管理组件，名字会出现在个别区块标题里，与你的操作无关 |
